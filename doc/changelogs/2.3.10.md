# ezoracle 2.3.10

Changes since 2.3.9.

- Updated: arrayQuery() reports an error raised while the rows are fetched (ORA-01722 on a row that does not convert,
  ORA-01555, a lost connection) instead of returning the rows fetched so far. It returns false, or throws
  eZDBException in exception mode, and the SQL query cache keeps nothing (pull request #3).
- Updated: arrayQuery() reports a statement that fails to run, and rows that fail to come, to the transaction, as
  query() and the MySQLi, PostgreSQL and SQLite drivers do: inside a transaction the error invalidates it and rolls it
  back. Before, the transaction carried on as if the read had worked.
- Updated: A read whose connection is lost while its rows are fetched (one of ReconnectErrors) is run again once on a
  new connection, outside a transaction and with RetryReads=enabled, as a read lost before it ran already was.
- Updated: The cluster backends (DFS and database) and the cluster gateways report an error raised while rows or a
  file are read:
  - _query() returns false instead of the rows fetched so far (file lists, purge lists);
  - _selectOne() and the gateways' metadata lookup report it instead of answering "no such file" (the gateway
    answers 500, not 404);
  - _selectOne() no longer ends in a TypeError on PHP 8 when its statement fails (oci_error() of a freed statement);
  - the LOB reads of the database cluster read a last chunk of "0" (it ended the loop and cut the file) and report a
    read that stops before the end.
- Added: tests/eZOracleFetchErrorTest.php, with a stand-in for the oci8 functions (tests/eZOracleOci8StandIn.php):
  no database is needed.

Upgrading: composer update and clear the caches. Code that runs arrayQuery() inside a transaction and expected false
on an Oracle error now sees the transaction rolled back, as on MySQL and PostgreSQL.
