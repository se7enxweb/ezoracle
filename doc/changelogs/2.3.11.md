# ezoracle 2.3.11

Changes since 2.3.10.

- Added: Oracle updates for the step from 5.3 to Exponential 6.0.0, the same changes as the kernel's MySQL and
  PostgreSQL files, which the Oracle side lacked:
  - update/database/ezpublish/5.4/dbupdate-5.3.0-to-5.4.0.sql: drops ezsearch_return_count and its sequence
    s_search_return_count (each only when it exists), stores an unset date or date and time attribute as NULL
    instead of 0 (ezcontentobject_attribute and ezinfocollection_attribute; skip these two statements when updating
    from 5.3.3 or higher, as the kernel's files say) and removes the ezuser_setting rows of users that no longer exist;
  - update/database/ezpublish/5.4/dbupdate-cluster-5.3.0-to-5.4.0.sql: with a DFS cluster, the scope 'images' of
    ezdfsfile becomes 'image' (nothing happens without the table);
  - update/database/ezpublish/6.0/dbupdate-5.4.0-6.0.0.sql: sets the version rows to 6.0.0, widens
    ezuser.password_hash from VARCHAR2(50) to VARCHAR2(255) only when it is narrower (a bcrypt hash of 60
    characters failed with ORA-12899 at sign-in) and adds ezcontentobject_trash.trashed (INTEGER DEFAULT 0 NOT NULL)
    only when it is missing, without which moving content to the trash fails. The renaming of the PostgreSQL
    sequences has no Oracle counterpart: the sequences keep their s_<table> names.
- Added: Oracle updates for the kernel tables and columns of Exponential 6.0.15 in update/database/ezpublish/6.0/,
  one PL/SQL file per feature, each table, column and index created only when missing: audit tables, bookmark
  folders, mail preferences, API keys, passkeys, transfer runs, data table connections and synchronisation, user
  sessions, user audit, help tables, upgrade steps, the migration record (with the copy of expupgrade_step), the PDF
  export footer, RSS OPML and podcast, REST PKCE and the 14 order statuses of 6.0.15.
- Updated: A fresh install on Oracle states every NOT NULL text column of the Exponential 6.0.15 kernel tables as
  nullable (147 ColumnOptionTranslations lines in settings/dbschema.ini.append.php), since Oracle stores an empty
  string as NULL and would refuse the rows the kernel writes.

Verified on Oracle 26ai Free in throwaway schemas: a 5.3 schema with rows, upgraded with the three new files and
run twice, matches a fresh install of the 6.0.0 kernel schema in tables, columns, defaults, nullability, indexes,
keys, sequences and triggers, and its data is as expected; a 6.0.0 schema upgraded with the 6.0.15 files, run twice,
matches a fresh install of the 6.0.15 schema.

Upgrading: composer update and clear the caches. A database on Oracle that comes from 5.3 or 5.4 runs, as the schema
owner with SQL*Plus or SQLcl, the files in update/database/ezpublish/5.4/ (the cluster file as the owner of the
cluster table) and dbupdate-5.4.0-6.0.0.sql, then the dbupdate-6.0.0-6.0.15-*.sql files. Every file can run again.
