# ezoracle 2.3.13

Changes since 2.3.12.

- Removed: The table expupgrade_step. Exponential 6.0.15 keeps the record of exp:upgrade in exp_migration; the table
  expupgrade_step belonged to a 6.0.15 pre-release only and is gone from the kernel schema, so no released version
  creates it. settings/dbschema.ini.append.php no longer names its columns, and
  update/database/ezpublish/6.0/dbupdate-6.0.0-6.0.15-upgrade-steps.sql creates nothing any more (it is kept so that a
  list of the 6.0.15 updates that names it still runs).
- Updated: update/database/ezpublish/6.0/dbupdate-6.0.0-6.0.15-migration-tables.sql retires a pre-release
  expupgrade_step: after copying its rows into exp_migration (a row exp_migration has already is kept), it checks that
  every row is there, stops with ORA-20001 and keeps the table if one is not, and then drops it with
  DROP TABLE expupgrade_step PURGE. Only when the table exists, so the file can run again.

Verified on Oracle 26ai Free in throwaway schemas: a database made with the 2.3.12 files for 6.0.15 (both tables, the
rows copied, one more row added afterwards) ends after the new file without expupgrade_step, with every row in
exp_migration, the newer row of exp_migration kept and nothing in the recycle bin; a second run changes nothing. A
database upgraded from a release runs the 6.0.15 upgrade-steps and migration-tables files twice and never has the
table.

Upgrading: composer update. A database that never ran a 6.0.15 pre-release has nothing to do. One that has
expupgrade_step: run dbupdate-6.0.0-6.0.15-migration-tables.sql again as the schema owner, or
./console exp:upgrade:database --apply (step 6.0.15-upgrade-record-table), which does the same.
