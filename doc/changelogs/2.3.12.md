# ezoracle 2.3.12

Changes since 2.3.11.

- Updated: update/database/ezpublish/5.0/dbupdate-4.7.0-to-5.0.0.sql no longer fails when users share an e-mail
  address. The digest settings of an address got their user id from a subquery that returned one row per user with
  that address (ORA-01427, ORA-30926 on 23ai and later); the lowest user id is taken now (MIN()), where the kernel's
  MySQL and PostgreSQL files take one of them with LIMIT 1. Settings of an address that belongs to no user are
  removed with NOT EXISTS instead of NOT IN, which removed nothing as soon as one user had no e-mail address (Oracle
  stores '' as NULL) and so failed with ORA-01407. Every step is done only when needed and the file can run again;
  eznode_assignment.remote_id becomes VARCHAR2(100) through a new column, as the 5.0 to 5.1 file does (the former
  MODIFY (remote_id TYPE ...) was not Oracle syntax, ORA-00907). The unstable 4.7.0 to 5.0.0alpha1 file has the same
  MIN() and NOT EXISTS.
- Updated: update/database/ezpublish/5.2/dbupdate-5.1.0-to-5.2.0.sql sets ezcontentobject.language_mask as the
  kernel's files do, (o.language_mask & 1) | (v.language_mask & ~1). It took only bit 0 of the version's mask, which
  cleared every language bit, failed with ORA-01427 when an object's current version is there twice, and needed the
  bitor() function.

The other Oracle update files have no subquery that can return more than one row for a single value.

Verified on Oracle 26ai Free in throwaway schemas: with two users sharing an e-mail address and a user without one,
the previous 4.7 to 5.0 file fails (ORA-01427 / ORA-30926, ORA-01407); the new one runs twice without an error, gives
the shared address the lowest user id and leaves no invalid object. The previous 5.2 statement fails with ORA-01427
on a duplicated current version; the new one sets the kernel's masks, also when run again.

Upgrading: composer update. A database that is already past 5.2 needs nothing. A database on Oracle that ran the
previous 5.1 to 5.2 file may have objects whose language_mask lost its language bits; running the EZP-21469
statement of the new file again (as the schema owner) sets them from the current versions.
