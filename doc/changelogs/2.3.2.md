# ezoracle 2.3.2

Changes since 2.3.1. The Oracle driver takes part in Exponential's SQL query cache
(settings/querycache.ini). Tested against Oracle AI Database 26ai Free (23.26) with
PHP 8.5 and oci8 3.4.1, on PHP-FPM and on Exponential Velocity.

## Added

- Added: The Oracle driver takes part in the SQL query cache. arrayQuery() asks the
  cache before it runs a SELECT and returns the cached rows while they are current,
  and stores the rows it read; query() reports every successful statement, so a write
  makes the results of its tables stale and an anonymous PL/SQL block all of them.
  The calls are skipped on a kernel without the cache.

## Updated

- Updated: Version 2.3.2

## Upgrading from 2.3.1

- Nothing changes until the cache is switched on: querycache.ini `Mode=off` is the
  kernel's default. With `Mode=request` or `Mode=shared` the driver uses it.
- Needs the Exponential kernel whose query cache knows Oracle's statements (never a
  sequence read such as `SELECT <sequence>.currval FROM DUAL`, the clock, `SYS_GUID`,
  `SYS_CONTEXT` or the catalogue; a PL/SQL block makes everything stale). With an
  older kernel that has the cache but not these rules, leave it off on Oracle: a
  cached sequence read would hand out a row id twice.
- Measured on one installation with `Mode=shared`: a publish from the admin edit
  form went from a median of 1.21 s to 1.10 s (Apache/PHP-FPM) and from 1.42 s to
  1.29 s (Exponential Velocity).
